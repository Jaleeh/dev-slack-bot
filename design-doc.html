dev-slack-bot

Bot architecture

An open-source, self-hosted chat bot that answers questions about a company's GitHub repositories, so project managers and support staff get answers without asking a developer. This document replaces the earlier learning-project design. Jira tickets, issue prioritisation and bug fixing return as future scope.

Implementation status. Design only. No code exists yet. Each choice below carries a badge: decided by the project owner, proposed and awaiting confirmation, or later for work deferred past the first release.

What this is

A non-technical person asks a question, such as how a business rule works or whether a reported problem is a bug or a setup issue. The bot reads the connected repositories and answers in the thread. It never changes code. Each company hosts its own copy and chooses its own model provider and region, so the company decides which country its data reaches. The project itself runs no servers and receives no data.

The project has two goals of equal weight: a product that is cheap to run and easy to set up, and a way for its maintainer to learn AI engineering with tools companies use. The second goal keeps evals and both retrieval methods in scope, and selects LangGraph, Postgres with pgvector and LangChain integrations over hand-written equivalents.

Mental model

Slack messages, or browser chat messages during a trial, reach a chat adapter, which converts them into a platform-neutral question. A LangGraph agent answers it using retrieval tools over local repository clones and a vector index in Postgres, and calls the chat and embedding providers the company configured through a PII redactor, which swaps personal data for placeholders on the way out and back on the way in. The admin UI writes settings and secrets through the FastAPI backend into Postgres. The FastAPI app and Postgres ship as one Docker Compose stack.

Layers

Chat adapters. One per platform: Slack and browser chat in the first release, Teams later.

Agent and retrieval. A LangGraph agent with retrieval tools. A setting selects direct repository search, vector search or both.

Providers. LangChain chat model and embedding integrations, each selected by a setting.

PII redactor. Replaces personal data and secrets with typed placeholders on every provider call, and restores them in replies.

Repository access. A GitHub App for production, a public URL or local folder for trials, and shallow local clones of each.

Setup and admin. A Next.js UI with a trial path and a full setup path, served as static files by the FastAPI app.

Evals. A labelled question set that scores retrieval, answers, cost and latency.

Architectural constraints

The first release is read only. The bot answers questions and changes nothing: no commits, no pull requests, no issue edits. Creating Jira tickets, prioritising issues and fixing bugs are future scope, set out under Future scope.
Each company decides where its data goes. The project fixes no region and no provider. The agent sends questions and the code it read to the chat provider, and the indexer sends code chunks to the embedding provider, so those two settings set the data location. The admin UI states the location beside each provider.
Personal data never reaches a provider unredacted. Every chat and embedding call passes through the PII redactor, whatever the provider, and nothing stored at rest holds real values except the encrypted placeholder mapping. Detection is imperfect, so the provider and region choice remains the second line of protection.
The project runs nothing and receives nothing. Maintainers publish code, Docker images and documentation. No central server, no shared GitHub App and no usage tracking sent back. Each company creates its own Slack app and GitHub App from manifests in the repository. LangSmith is excluded for the same reason: it is a hosted tracing service, so tracing uses Langfuse, which a company can host itself.
A trial takes minutes on a laptop. docker compose up, pick a model, point at a repository and chat in the browser. No Slack app, no GitHub App and no public URL. A trial and a production install run the same image; moving to production fills in more settings rather than reinstalling.
Nothing needs a public URL in the first release. Slack connects through Socket Mode, an outbound connection, and repositories refresh by polling, because GitHub webhooks and the Teams Bot Framework both need an HTTPS endpoint reachable from the internet.
Cheap to run for the hosting company. Model tokens are the main running cost, so every question has a limit on tool calls and tokens, and prompt caching is on where the provider supports it. The required stack is two containers: the FastAPI app, which also serves the admin UI, and Postgres. Langfuse is optional.
Secrets stay on the server. Model keys, Slack tokens and GitHub credentials are stored encrypted in Postgres and never returned to the browser after saving. The admin UI requires a login from the first release, because admins enter those secrets there.

Agent and retrieval

LangGraph agent

Answers one question with retrieval tools, within the per-question budget set under constraints. decided

Both retrieval methods are built decided. A setting such as RETRIEVAL=direct|vector|hybrid selects which tools the agent receives decided. The evals choose the default. Conversation state lives in Postgres through the LangGraph Postgres checkpointer decided.

retrieval methods 3 settings
direct tools: grep, read_file

The agent searches the clone as a developer would. Needs no index and no embedding provider, so a trial can start here. Can use more tokens per question than vector search.

vector tool: vector_search

Code is split into chunks, embedded and stored with pgvector through langchain-postgres decided. A refresh re-indexes only changed files. Needs an embedding provider.

hybrid all three tools

The agent picks per step. Its cost and accuracy come from the evals.

Providers

chat and embedding providers

Changing provider changes settings, not code. decided

Chat models come from LangChain integrations (langchain-anthropic, langchain-aws, langchain-openai, langchain-ollama) through init_chat_model decided. LiteLLM was considered and dropped, because LangGraph already uses these integrations and a second layer would duplicate them. Embeddings use a separate EMBEDDING_PROVIDER setting decided, because Anthropic offers no embeddings API. Options include Ollama (nomic-embed-text), Bedrock (Titan or Cohere) and OpenAI.

Technical hosts set provider settings as environment variables. The admin UI writes the same settings for everyone else, and an environment variable takes precedence decided. Each provider in the UI has a Test connection button.

providers and data location 4 entries
Ollama, vLLM your own machine or server

Data stays on the host and tokens cost nothing. Answer quality depends on the model, and a good model needs a capable GPU.

AWS Bedrock AWS region the company selects

The usual deployment runs the bot in the company's own AWS account, in the same region, with an IAM role on the server, so no key is copied. Cross-region inference profiles can route requests to other regions. Staying in one country needs the in-region model ID or a country-specific inference profile, which not every model offers in every region.

Azure OpenAI, Google Vertex cloud region the company selects

Data stays in the selected region when the region is set correctly.

Anthropic API, OpenAI API mostly US

Easiest setup: paste a key. Data usually leaves the company's country, and the admin UI says so.

PII redaction

PII redactor

Swaps personal data for typed placeholders before every provider call, and swaps the real values back before a reply reaches the user. decided

A user who asks "why can't Jane Citizen (jane@acme.com) log in?" sends the model "why can't <PERSON_1> (<EMAIL_1>) log in?". The model answers in placeholders, and the restorer puts the real values back in the reply. Typed placeholders were chosen over realistic fake data decided, because a realistic fake name can collide with a real name in the code, and an exact token restores without ambiguity. Detection uses Microsoft Presidio with a spaCy model, running inside the app container so no text leaves the host for detection decided. The spaCy model makes the image larger.

rules 8 rules
Every provider call one choke point

Redaction wraps every call to the chat and embedding providers, not only the user's question. grep results, file contents, seed data and test fixtures can hold real names and emails, and code chunks reach the embedding provider during indexing.

One mapping per thread encrypted, expires

The same value gets the same placeholder on every turn of a thread, so the model can follow the conversation. The mapping holds the real values, so it is stored encrypted in Postgres, deleted after a set period and never logged.

Redacted everywhere at rest logs, traces, history

App logs, Langfuse traces and the LangGraph checkpointer store only redacted text. Real values exist only in the mapping and in the reply sent back to the chat platform.

Secrets too keys, passwords, tokens

API keys and passwords committed to a repository are masked before any provider call, with the same placeholder scheme.

Allow-list editable in the admin UI

Company names, product names and code identifiers such as a class called Jordan would otherwise be flagged as people and break answers about the code.

Country recognisers enabled per company

Phone, tax and health identifiers differ by country. Admins enable the Presidio recognisers that match their country.

Tolerant restore case, possessives, leftovers

The restorer accepts changed case and possessive forms of a placeholder. A placeholder it cannot restore stays visible and is flagged, rather than dropped silently.

On by default, and visible every provider, Ollama included

Redaction is on for every provider and an admin can turn it off. Each reply carries a short note when values were hidden, such as "2 names were hidden from the model".

Detection misses some names, IDs and free text, so redaction lowers the risk without removing it. The evals measure the catch rate, and the detector favours over-redaction when unsure.

Production source. A Connect GitHub button runs the install flow for the company's own GitHub App, then lists repositories as checkboxes. The bot clones and reads only the ticked ones.

Trial source. Needs no GitHub App.

Scheduled shallow refresh decided

Shallow clones (--depth 1) pulled on an adjustable interval. Shallow clones save disk and network but drop history, so the bot cannot answer who changed something or when. Webhooks would refresh sooner but need a public URL.

Evals

evals

Measures retrieval and answers before and after every change. decided

eval set 5 items
Labelled questions question, correct files, known answer

Written against a public sample repository, so anyone can run them and the set holds no company data.

Retrieval metrics recall@k, MRR

Compares direct, vector and hybrid retrieval, and chunk size and embedding model for vector search. Picks the default retrieval setting.

Answer metrics faithfulness to source

Checks each answer against the code it retrieved.

Cost and latency tokens, cost, seconds per question

Recorded per run, and in production through optional Langfuse tracing decided.

Redaction catch rate planted fake PII found

Text with planted fake names, emails, IDs and secrets, scored on how much the redactor finds and how much code it wrongly flags.

Evals run from the command line. CI runs only the retrieval checks, because answer evals spend tokens and CI runners have no GPU for a local model decided.

Future scope

write actions

Capabilities after the read-only first release. None is built yet.

capabilities 3 capabilities
Create Jira tickets later

Turns a chat thread, such as a confirmed bug, into a Jira ticket. Adds a Jira connection to setup and a Jira tool to the agent.

Prioritise issues later

Suggests priority and the code area involved for incoming issues, using the same retrieval tools as question answering.

Fix bugs later

The largest addition. The earlier design ran fixes as background jobs: a queue, a sandbox that clones the repository and runs a coding agent, and a draft pull request at the end. That needs GitHub write access, so the GitHub App gains write permissions for companies that turn it on.

Every write waits for a person. decided Creating a ticket, changing a priority or opening a pull request happens only after someone presses confirm in the chat thread. The bot first posts a preview of the write. LangGraph's human-in-the-loop interrupt pauses the agent until the button is pressed proposed.

The first release reads repository code only. Logs, customer configuration and tickets would help tell a bug from a setup issue, and arrive later as extra agent tools. Each one adds personal data to what reaches the model, so each needs its own privacy review.

The first release keeps these possible without building them: the agent takes tools from a list, so a Jira tool is one more entry, and the adapter boundary already carries replies back to the thread.

Skills learned

The project mainly teaches AI engineering: building products on top of models. It covers little ML engineering, which trains and serves the models themselves.

skill areas 6 areas
AI engineering the core of the project

Agent design with tool use in LangGraph. Retrieval: chunking, embeddings, pgvector, hybrid search, and comparing direct against vector retrieval. Evals: labelled sets, recall@k, MRR, faithfulness. Working across providers, controlling cost and latency with token limits and prompt caching, tracing with Langfuse, conversation memory with the Postgres checkpointer, and running local models with Ollama.

Data privacy and security provider and secrets choices

Data residency and region selection, including Bedrock in-region and cross-region inference. Reversible PII redaction with Presidio: detection, typed placeholders, per-thread mappings and restore. Encrypted secrets that never return to the browser. PII trade-offs. Least-privilege access through GitHub Apps and IAM roles.

Backend and integrations FastAPI app

FastAPI, SQLAlchemy and Alembic, Postgres with pgvector, Slack Bolt with Socket Mode and app manifests, GitHub App authentication and repository syncing, and an adapter design that admits a second chat platform.

Frontend admin UI

Building the admin UI as a static Next.js site, and designing a setup wizard for non-technical users.

Shipping and open source packaging and documentation

Docker Compose and images on GHCR, GitHub Actions CI with evals, setup documentation a stranger can follow, and design documents, ADRs and specs.

Not covered ML engineering

Training and fine-tuning models, data labelling pipelines at scale, GPU serving, and MLOps such as drift monitoring and retraining.

Design principles

  1. Slack first, and no more scope than the first release needs. The adapter boundary keeps Teams possible. Nothing for Teams is built until Slack works.
  2. The safe setup is the easy setup. The admin UI states where each provider processes data, so a non-technical admin makes the location choice knowingly.
  3. One set of settings, two ways to write it. Environment variables and the admin UI write the same settings, so a technical host and a non-technical admin end up with the same system.
  4. Measure before changing. The eval set exists before the retrieval code it scores, so every change shows up as a number.
  5. Industry-standard tools over custom code. Where a widely used library covers a need, use it. A self-hoster's team is more likely to know it, and the maintainer learns tools companies hire for.

Open questions

  • Eval framework. Ragas or promptfoo. Not chosen.
  • How a production install is first started. A one-click deploy on a hosting site, or a server that IT provides. Hosted deploy buttons often default to a US region.
  • Audit log and admin history. Whether the first release records who asked what. The earlier design required a full audit log. This design has not decided.
  • Where bug fixing stops. The earlier design ended bug fixes at a draft pull request that a person reviews and merges. This design has not yet decided whether that rule carries over.
  • Project name. The repository is called dev-slack-bot, which no longer fits a multi-platform bot.
