# Step 2.2: Question Set Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A labelled set of about 30 business questions over django-oscar `4.2.1`, plus a format check that loads it into frozen models and rejects bad entries by name.

**Architecture:** `evals/question_set.py` holds frozen Pydantic models and one loader. The rules live in model validators, so tests call `QuestionSet.model_validate(dict)` with no file I/O. Only `load_question_set(path)` reads YAML. The data lives in `evals/datasets/questions.yaml`.

**Tech Stack:** Python 3.14, Pydantic v2 (already installed via pydantic-settings), PyYAML (new), pytest, Ruff, mypy (strict).

**Spec:** [`docs/specs/2026-10-24-step-2-evals.md`](../specs/2026-10-24-step-2-evals.md), section "2.2 Question set"

## Global Constraints

- Branch `step-2.2-question-set`. One PR: the data and its format check.
- Sample repo: `django-oscar`, tag `4.2.1`. Scope: `basket`, `offer`, `voucher`, `shipping`, `checkout`, `order`, `partner` under `src/oscar/apps/`. No dashboard, no migrations.
- About 30 questions: about 24 `how_it_works`, about 6 `bug_or_setup`.
- 2–5 key facts and 1–4 files per question.
- Questions use plain business wording. No function, class or file names.
- Key facts are written for a non-technical asker with no context: no Oscar terms (stock record, range, strategy, application), no description of how the code works inside, only what the asker needs to know.
- Paths are repo-relative, e.g. `src/oscar/apps/offer/applicator.py`.
- The file-exists-at-tag check is **not** in this slice (it's 2.3).
- **Commit only when the user says so.**

## Builder's calls

- **Module name `question_set.py`, not `datasets.py`.** A `datasets.py` beside a `datasets/` folder is confusing to read, even though Python picks the `.py`. 2.4 adds `pii_set.py` the same way.
- **Two rules beyond the spec,** both cheap and both guard something the spec cares about:
  - Paths must be normalised (`./src/a.py`, `src//a.py`, `src/a/` rejected). 2.1 compares paths exactly, so an unclean path would silently score 0 forever.
  - Questions must not contain `_`, a backtick, `.py` or `()`. This catches the most common developer-speak (the spec's anti-goal). It won't catch `CamelCase` names; maintainer review covers those.
- **Unknown keys are rejected** (`extra="forbid"`), so a typo like `key_fact:` fails instead of being dropped.
- **PyYAML goes in the `dev` group**, with `types-PyYAML` for mypy. Evals don't ship in the app image (`uv sync --no-dev`).

## Review Focus

1. **A typo'd key** (`file:` instead of `files:`). Must fail, not be ignored. Tested in Task 1.
2. **A non-normalised path** (`./src/a.py`). Must fail, since retrieval scoring would never match it. Tested in Task 1.
3. **An empty or whitespace-only key fact or id** (`- ""`). Must fail; a blank fact can't be graded. Tested in Task 1.
4. **An empty YAML file or a list at the top level.** Must fail with a Pydantic error, not an `AttributeError`. Tested in Task 1.
5. **A question naming code** (`what does apply_offers do?`). Must fail. Tested in Task 1.

### Task 1: Format check

**Files:**
- Modify: `backend/pyproject.toml`: add `pyyaml` and `types-pyyaml` to the `dev` group (`uv add --dev pyyaml types-pyyaml`)
- Create: `backend/evals/question_set.py`
- Create: `backend/tests/unit/evals/test_question_set.py`

**Interfaces:**
- Produces (used by the 2.3 runner):
  - `QUESTIONS_PATH: Path`, pointing at `evals/datasets/questions.yaml`
  - `class Question(BaseModel)`, frozen: `id: str`, `type: Literal["how_it_works", "bug_or_setup"]`, `question: str`, `key_facts: tuple[str, ...]`, `files: tuple[str, ...]`
  - `class QuestionSet(BaseModel)`, frozen: `version: int`, `repo: str`, `ref: str`, `questions: tuple[Question, ...]`
  - `load_question_set(path: Path) -> QuestionSet`. Raises `pydantic.ValidationError` on a bad file.

- [ ] **Step 1: Write the failing tests** in `tests/unit/evals/test_question_set.py`.

Arrange with two module-level factories that return plain dicts:
- `a_question(**overrides)`: a valid entry with id `q1`, type `how_it_works`, one plain question, two facts, one path `src/oscar/apps/offer/applicator.py`, then the overrides applied.
- `a_question_set(*questions)`: `{"version": 1, "repo": "django-oscar", "ref": "4.2.1", "questions": list(questions)}`.

Every rejection test is one `QuestionSet.model_validate(...)` inside `pytest.raises(ValidationError, match=...)`.

| Test name | Input | Expected |
|---|---|---|
| `test_a_valid_set_loads` | `a_question_set(a_question())` | `.questions[0].files == ("src/oscar/apps/offer/applicator.py",)` |
| `test_loaded_questions_cannot_be_changed` | assign `.questions[0].id = "x"` on a loaded set | `ValidationError` |
| `test_rejects_a_missing_id` | question with `id` key removed | match `"id"` |
| `test_rejects_a_blank_id` | `id="  "` | match `"id"` |
| `test_rejects_a_duplicated_id` | two questions, both `id="q1"` | match `"q1"` |
| `test_rejects_an_unknown_type` | `type="trivia"` | match `"type"` |
| `test_rejects_no_key_facts` | `key_facts=[]` | match `"q1"` |
| `test_rejects_a_blank_key_fact` | `key_facts=["A fact.", ""]` | match `"key_facts"` (a field-level error, so Pydantic names the field and index, not the id) |
| `test_rejects_no_files` | `files=[]` | match `"q1"` |
| `test_rejects_an_absolute_path` | `files=["/src/a.py"]` | match `"q1"` |
| `test_rejects_a_path_that_climbs_out` | `files=["src/../a.py"]` | match `"q1"` |
| `test_rejects_a_path_that_is_not_normalised` | `files=["./src/a.py"]` | match `"q1"` |
| `test_rejects_a_question_that_names_code` | `question="What does apply_offers do?"` | match `"q1"` |
| `test_rejects_an_unknown_key` | `a_question(file=["src/a.py"])` | match `"file"` |
| `test_rejects_a_top_level_that_is_not_a_mapping` | `QuestionSet.model_validate(None)` | `ValidationError` |
| `test_load_reads_a_yaml_file` | write a one-entry YAML to `tmp_path`, call `load_question_set` | `.repo == "django-oscar"` |

- [ ] **Step 2: Run the tests to check they fail**

Run: `cd backend && uv run pytest tests/unit/evals/test_question_set.py -v`
Expected: FAIL with `ModuleNotFoundError: No module named 'evals.question_set'`

- [ ] **Step 3: Implement `evals/question_set.py`** with the interfaces above.

- Both models: `ConfigDict(frozen=True, extra="forbid")`. Use a shared `Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]` for `id`, `question`, each fact and each path.
- `Question` gets one `model_validator(mode="after")` that checks: facts and files not empty, each path rules (absolute, contains `..`, `PurePosixPath(path).as_posix() != path`), and the question text for `_`, `` ` ``, `.py`, `()`. Every message starts with the question's id, e.g. `"q1: files is empty"`.
- `QuestionSet` gets one `model_validator(mode="after")` that names any duplicated id.
- `load_question_set` is `QuestionSet.model_validate(yaml.safe_load(path.read_text()))`.
- Keep each validator small. If one grows, extract the path rule into `_path_problem(path: str) -> str | None`.
