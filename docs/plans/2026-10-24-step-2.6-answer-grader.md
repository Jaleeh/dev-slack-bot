# Step 2.6: Answer Grader Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Grade an answer fact by fact, plus one faithfulness check, with a local Ollama model. Prove the grader on a set of planted right and wrong answers with `make eval-answers`.

**Architecture:** `evals/settings.py` reads the model settings and builds the judge with `init_chat_model`. `evals/answer_set.py` loads `wrong_answers.yaml` and checks it against the question set. `evals/grader.py` asks the judge one yes/no question per check, retries an unreadable reply once, and decides whether the grader got each answer right. `evals/answer_runner.py` grades the whole set, prints a summary and saves a results file. The git-commit helper moves out of `runner.py` so both runners share it.

**Tech Stack:** Python 3.14, Pydantic v2, pydantic-settings, `langchain` 1.4, `langchain-ollama` 1.1, pytest, Ruff, mypy (strict). Local model `ornith:9b` (already pulled on the maintainer's machine).

**Spec:** [`docs/specs/2026-10-24-step-2-evals.md`](../specs/2026-10-24-step-2-evals.md), section "2.6 Answer grader"

## Global Constraints

- Branch `step-2.6-answer-grader`. One PR, code and data, the only slice allowed both.
- Two checks per answer: per key fact "Does the answer state this fact?", and once per answer "Does the answer claim anything the retrieved code doesn't support?". Temperature 0.
- Inputs: the question, its key facts, the answer, the retrieved code text.
- Settings, read by their own class in `evals/`, from the repo-root `.env`:

| Variable | Default |
|---|---|
| `CHAT_MODEL` | `ollama:ornith:9b` |
| `EVAL_JUDGE_MODEL` | empty → copies `CHAT_MODEL` |
| `OLLAMA_BASE_URL` | `http://localhost:11434` |

- An unreadable reply is retried once, then recorded as `ungraded`. Never a pass.
- Grader is right: on a `correct` answer, when every fact is stated and faithfulness is clean. On a `wrong` answer, when its named check fails. Any `ungraded` check makes that answer **inconclusive**, which counts as wrong.
- Results file fields: `started_at`, `git_commit`, dataset version, judge model and settings, counts (right, wrong, inconclusive), per-check rows.
- `make eval-answers` stops with a clear message if Ollama isn't reachable.
- Planted answers use plain words for a non-technical reader: no code terms, no library terms.
- **Commit only when the user says so.**

## Builder's calls

- **Replies are read with `judge.with_structured_output(Verdict)`.** On Ollama this uses [structured outputs](https://docs.ollama.com/capabilities/structured-outputs): `ChatOllama` sends the JSON schema as `format`, so decoding is held to the schema, and then it reads the reply with `PydanticOutputParser` (read in `langchain-ollama` 1.1 source).
- **Unit tests use a `FakeJudge`**, a subclass of LangChain's `FakeListChatModel` in `backend/tests/fake_judge.py`. LangChain's fake models raise `NotImplementedError` on `with_structured_output` (checked on `langchain-core` 1.7), so `FakeJudge.with_structured_output(schema)` returns `self | PydanticOutputParser(pydantic_object=schema)`. That is the same parser `ChatOllama` uses, without the schema constraint, so a garbage reply raises the same `OutputParserException`.
- **Ollama down is a stop, not `ungraded`.** Only `OutputParserException` retries. `httpx.ConnectError` (Ollama not running) and `ollama.ResponseError` (model not pulled) stop the run with exit code 1, like a broken dataset in `make eval`. Both types were checked by probe and are pinned in the learning tests.
- **The retry asks more plainly.** At temperature 0 the same prompt gives the same reply, so the retry adds "Reply with only yes or no." A reply that isn't a `Verdict` (another provider returning `None` or a bare dict) also counts as unreadable.
- **Judge model and faithfulness prompt (decided 2026-10-25 by probe, after the first full run).** `ornith:9b` missed 3 of 5 made-up details. The grader is now `gemma4:e4b` (thinking on by default), set as `EVAL_JUDGE_MODEL` in `.env.example`. The faithfulness question asks "is every rule, limit, number and behaviour supported?", so yes means faithful, and the judge may reply `unclear` when the code shown isn't enough. `unclear` makes the answer inconclusive, never a pass. The retry nudge became "Reply with only the one word asked for." ADR-004 records the full comparison.
- **`base_url` is passed only for `ollama:` models.** Passed to `anthropic:`, it would point Anthropic's client at Ollama.
- **`langchain` and `langchain-ollama` go in the `dev` dependency group**, next to `pyyaml`, because evals aren't in the Docker image. Step 3 moves them to the main dependencies when the bot needs them.
- **Module names:** `answer_set.py` (dataset), `grader.py` (checks and outcome), `answer_runner.py` (`make eval-answers`), `settings.py`, and `run_record.py` (the git commit, moved out of `runner.py`).
- **`wrong_answers.yaml` format:**

```yaml
version: 1
answers:
  - question_id: offer-repeat
    code: |
      # src/oscar/apps/offer/benefits.py
      ...hand-picked lines...
    correct: "Plain-words answer stating every key fact."
    wrong:
      - kind: made_up_detail     # wrong_rule | made_up_detail | vague | other_question
        fails: faithfulness      # faithfulness | fact-N (1-based key fact number)
        answer: "..."
```

- **Format check:** `question_id` exists in `questions.yaml` and is unique. `fact-N` is within that question's key facts. `code` is at most 80 lines and starts with a `# <path>` line. Each entry has at least 2 wrong answers. Each of the 4 kinds appears at least twice across the set.
- **Which check each kind names:** `made_up_detail` → `faithfulness` (the answer otherwise states every fact). `wrong_rule` → the fact it contradicts. `vague` and `other_question` → `fact-1`.
- **Outcomes are per answer.** Counts are over answers. The summary prints one line per entry, with each answer's outcome.
- **The results file is `results/answers-<timestamp>.json`**, so it sits beside `make eval`'s files without clashing.
- **Prompts** (exact wording; the schema, not the prompt, fixes the reply's shape):

```text
FACT_PROMPT:
You are checking an answer given to a non-technical person about how an online shop works.
Question: {question}
Answer: {answer}
Fact: {fact}
Does the answer state this fact? The wording may differ, but the meaning must match. Reply yes or no.

FAITHFULNESS_PROMPT:
You are checking an answer against the shop's code it was based on.
Code:
{code}
Question: {question}
Answer: {answer}
Does the answer claim anything this code doesn't support? Reply yes or no.
```

## Review Focus

1. **Ollama not running.** `make eval-answers` prints `eval-answers stopped: ...` naming the URL, and exits 1 with no traceback. Tested in Task 4.
2. **The judge model isn't pulled.** Same clean stop, naming the model. Tested in Task 4.
3. **A reply that's prose, not JSON, twice in a row.** The check is `ungraded`, the answer is inconclusive, and the summary shows the ungraded count. Tested in Tasks 3 and 4.
4. **A wrong answer that fails its named check but has another check ungraded.** Inconclusive, not right. Tested in Task 3.
5. **`wrong_answers.yaml` names a question or fact number that doesn't exist.** The run stops with the entry's `question_id` before any model call. Tested in Tasks 2 and 4.

  - `class Verdict(BaseModel)`: `answer: Literal["yes", "no"]`
  - `CheckOutcome = Literal["pass", "fail", "ungraded"]`. A fact passes on "yes". Faithfulness passes on "no".
  - `class CheckResult`: `check: str`, `outcome: CheckOutcome`
  - `class Grade`: `checks: tuple[CheckResult, ...]` (facts in order, then faithfulness); property `fact_score -> float` (share of fact checks that passed, ungraded counts as not stated)
  - `grade(judge: BaseChatModel, question: Question, answer: str, code: str) -> Grade`
  - `Outcome = Literal["right", "wrong", "inconclusive"]`
  - `outcome_for_correct(grade: Grade) -> Outcome`, `outcome_for_wrong(grade: Grade, wrong: WrongAnswer) -> Outcome`. Both pure. Any ungraded check → `"inconclusive"`.

|---|---|---|
