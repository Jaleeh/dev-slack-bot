# Step 2: Evals

**Date:** 2026-10-24
**Status:** approved
**Build order:** step 2 of 7 in the [design doc](../../design-doc.html)

## Intent

Build the fixed test set that scores every later step, before any bot code exists. Two decisions depend on it most:

1. **Which retrieval method to use** (direct, vector or hybrid, decided in step 7).
2. **Whether personal data leaks** to a model provider (the redactor, built in step 4).

The people asking the bot questions are project managers and support staff. They ask how a business rule works, or whether a problem is a bug or a setup issue. They never need file names. The answer key still records files, because the retrieval score needs them.

Everything is hand-written so the maintainer can see how each score works. This is a learning goal of the project (see the design doc's goals). Ragas can come later as an optional cross-check. It is not part of this step.

## Success

When all six slices are merged:

1. `make eval` on a fresh clone fetches the sample repository, scores retrieval and PII with stand-ins, prints a summary table, and saves a results file. It needs no model and no network beyond the first fetch.
2. `make eval-answers`, with Ollama running, grades a set of answers. It passes every correct answer and fails every planted wrong answer.
3. `make test` and `make lint` pass.
4. The maintainer has reviewed and accepted the question set and the PII set.

## Goals

- A labelled question set over a public sample repository.
- A fake PII set in UK formats, with look-alikes that must not be flagged.
- Pure scoring functions: recall@k, MRR, PII catch rate, wrong-flag rate.
- An AI grader that checks answers fact by fact, running on a local Ollama model.
- A runner that saves every run's numbers together with the setup that produced them.

## Non-goals

- **The bot.** The agent and retrieval tools are step 3. This step defines the interface they plug into.
- **The redactor.** Presidio is step 4. This step defines the interface it plugs into.
- **Pass bars.** Runs record numbers only. Thresholds come later, once there are real numbers to set them from.
- **CI.** It is postponed until the project is closer to production.
- **Ragas or promptfoo.**
- **A second sample repository.** The format allows one later (see `repo` below), but nothing is built for it.
- **The maintainer's one-off hand-check of the grader.** It needs real bot answers, so it happens in step 3.
- **Langfuse.**

## Anti-goals

- **A score that can't fail.** Every metric must be shown to move: a test where it scores 0 and a test where it scores 1.
- **Fake PII that is too fake.** A value that doesn't look like real data (`12345678901`, a card number that fails its checksum) passes through any detector unnoticed, so the catch rate measures nothing.
- **Real people's data anywhere in the repository.**
- **Silent grader failures.** A grader reply that can't be read is recorded as ungraded, never as a pass.
- **Developer-speak questions.** A question that names a function or file ("what does `apply_offers` do?") tests grep, not understanding.

## Sample repository

[django-oscar](https://github.com/django-oscar/django-oscar), pinned to tag **`4.2.1`**. BSD-3 licence.

- **Why:** it is real e-commerce code with business rules spread across files (offers, vouchers, basket, shipping, checkout, order status, stock). The maintainer knows Django and can check answers.
- **Scope:** the core apps under `src/oscar/apps/`: `basket`, `offer`, `voucher`, `shipping`, `checkout`, `order`, `partner`. The admin dashboard and migrations are out of scope.
- **Pinned:** the tag never moves, so the answer key never drifts from the code.
- **Rejected:** `cosmicpython/code` (37 Python files, too small to tell retrieval methods apart, CC-BY-ND), `dotnet/eShop` (a good runner-up in C#, kept for a later second repo), `microservices-demo` and `spring-petclinic` (too few business rules).

The bot itself stays language-agnostic. Oscar is only the first test repository.

### 2.1 Retrieval maths

Two pure functions over one question:

- **recall@k** is the share of the question's correct files found in the top *k* of the ranked results. With 2 correct files and 1 of them in the top 5, recall@5 = 0.5.
- **reciprocal rank** is `1 / rank` of the first correct file, or 0 if none is found.

The run-level figures are the mean over all questions: mean recall@k and MRR (mean reciprocal rank).

- Report **k = 5 and k = 10**. *Our call.*
- File paths are compared exactly, relative to the repository root.
- Duplicate paths in the results count once, at their first rank.
- A question with no correct files is invalid. The format check in 2.2 rejects it, so the maths may assume at least one.

**Tests:** perfect results score 1.0, no correct files found scores 0.0, plus a partial case and the duplicates rule. Expected values are hard-coded, never computed in the test.

**Docs:** add an ADR, *ADR-001: how answers and retrieval are evaluated*. It records hand-written evals over Ragas and promptfoo, and why (learning, no hidden prompts). Update the "framework (Ragas or promptfoo) is chosen in step 2" line in `tech-stack.md`. Mark the design doc's open question "Eval framework" as decided.

### 2.2 Question set

`datasets/questions.yaml`. Claude drafts it, and the maintainer reviews every entry.

```yaml
version: 1
repo: django-oscar
ref: 4.2.1
questions:
  - id: voucher-after-offers
    type: how_it_works            # or bug_or_setup
    question: "If a customer has a voucher and there's also a sale on, which discount applies first?"
    key_facts:
      - "Site offers are applied to the basket before vouchers."
      - "..."
    files:
      - src/oscar/apps/basket/abstract_models.py
      - src/oscar/apps/offer/applicator.py
```

*(The example's facts and files are for illustration only. The real entries are written and checked against the code at `4.2.1`.)*

- **~30 questions**, about 24 `how_it_works` and 6 `bug_or_setup`. *Our call.*
- **Plain business wording.** No function, class or file names in the question.
- **2–5 key facts** per question. Each is one short statement a reader can check as true or false against the answer.
- **1–4 files** per question. These are the files a developer would need to read to answer it, not every file that mentions the topic.
- `repo` and `ref` sit at the top of the file, so a second repository later is a second file, not a format change.
- Spread the questions across all seven core apps, and include some whose answer needs more than one app (for example, offers and baskets).

**Format check** (`datasets.py`): loads the YAML into frozen Pydantic models and rejects it, with a message naming the entry, when:

- an `id` is missing or duplicated
- `type` is not one of the two values
- `key_facts` or `files` is empty
- a path is absolute or contains `..`

The check that every file exists at the tag comes in 2.3, which is the slice that fetches the repository.

**Tests:** the real `questions.yaml` passes, and each rejection rule has a small bad example that fails.

### 2.3 Runner

**Fetching the sample repo:** `sample_repo.py` makes a shallow clone of `django-oscar` at `4.2.1` into a git-ignored cache folder (`backend/evals/.cache/`, *our call*) and reuses it on later runs. A failed fetch stops the run with a clear message.

**Every listed file exists:** before scoring, the runner checks that every `files` entry exists in the clone, and stops with the list of missing paths if any is absent.

**The retrieval interface.** This is the seam step 3 plugs into:

```python
class Retriever(Protocol):
    name: str
    def retrieve(self, question: str) -> list[str]: ...   # ranked repo-relative paths
```

Step 2 ships one stand-in, `AnswerKeyRetriever`, which returns each question's correct files. It should score 1.0, which proves the plumbing works end to end. Step 3 adds the real retrievers.

**Results file:** each run writes `backend/evals/results/<UTC timestamp>.json`. The folder is git-ignored.

| Field | Holds |
|---|---|
| `started_at` | Aware UTC datetime |
| `git_commit` | The commit of this repo at run time |
| `dataset_version`, `repo`, `ref` | From `questions.yaml` |
| `retriever` | The retriever's `name` |
| `metrics` | Mean recall@5, recall@10, MRR |
| `questions` | Per question: id, ranked results, recall@5, recall@10, reciprocal rank, `seconds`, `tokens` |

`seconds` is measured around each `retrieve` call. `tokens` is a typed optional, empty for the stand-in and filled once a model is involved. Both exist now so the results format doesn't change in step 3.

The terminal prints a short summary table with the metrics and the results file path.

**Make:** `make eval` runs the runner on the host with `uv run`. It needs no Ollama and no database.

**Tests:** an integration test runs the runner against a tiny local git repository made inside the test (not Oscar, so the test needs no network). It checks that the results file holds the expected metrics. The stand-in scoring 1.0 against real Oscar is checked by running `make eval`, not by a unit test.

**Docs:** `project-structure.md` shows what now exists under `evals/`. README gets a line for `make eval`.

### 2.4 PII set

`datasets/pii.yaml`: ~25 snippets with ~50 planted values. Claude drafts it, and the maintainer reviews it.

```yaml
version: 1
snippets:
  - id: checkout-question
    kind: question                  # or code
    text: "Why can't John Doe (john.doe@example.com, 07700 900123) check out?"
    planted:
      - { type: PERSON, value: "John Doe" }
      - { type: EMAIL, value: "john.doe@example.com" }
      - { type: PHONE, value: "07700 900123" }
    lookalikes: []
  - id: settings-file
    kind: code
    text: |
      ALLOWED_HOSTS = ["example.com"]
      SUPPORT_EMAIL = "jane.roe@example.com"
    planted:
      - { type: EMAIL, value: "jane.roe@example.com" }
    lookalikes: ["example.com", "ALLOWED_HOSTS"]
```

- **About half questions, half code.** Questions sound like support staff. Code looks like real settings files, fixtures, logs and comments.
- **Every value is fake but realistic**, using ranges reserved for examples:

| Type | Source of fake values |
|---|---|
| PERSON | `John Doe`, `Jane Roe`, and a few clearly invented names from different backgrounds |
| EMAIL | Any address at `example.com`, `example.org` or `example.net` (reserved by RFC 2606) |
| PHONE | Ofcom drama ranges: mobiles `07700 900000`–`900999`, London `020 7946 0000`–`0999`, in both `0…` and `+44 …` forms |
| UK_NINO | `QQ` prefix, which is never issued (e.g. `QQ 12 34 56 C`) |
| CARD | Well-known test cards that pass the Luhn checksum (e.g. `4111 1111 1111 1111`) |
| IP | Documentation ranges from RFC 5737 (`192.0.2.x`, `198.51.100.x`, `203.0.113.x`) |
| SECRET | Vendors' published example keys (e.g. AWS's `AKIAIOSFODNN7EXAMPLE`) and obviously fake tokens |
| ADDRESS, DATE_OF_BIRTH | Invented streets and towns, with dates given next to a name |

- **Look-alikes** are things a careless detector would flag but must not: variable names (`user_email`, `phone_number`), bare domains, version strings (`4.2.1`), order numbers in Oscar's own format, dates that aren't birthdays, hex commit hashes.
- **Format check:** the same approach as 2.2. Every `planted` value and every look-alike must appear exactly in its `text`, ids are unique, and `type` is from the table above. For `PERSON` and `ADDRESS` values, no word of 3 or more letters may appear elsewhere in the `text` (see 2.5).

**Tests:** the real `pii.yaml` passes the format check, and each rejection rule has a failing example.

### 2.5 PII scoring

**The redaction interface.** This is the seam step 4 plugs into:

```python
class Redactor(Protocol):
    name: str
    def redact(self, text: str) -> str: ...
```

Scoring looks only at the redacted text, so it works with any redactor.

- **Caught:** a planted value counts as caught when its exact text no longer appears in the output. For `PERSON` and `ADDRESS` it must also lose every word of 3 or more letters, so `John <PERSON>` still leaks `John` and counts as a miss. Other types (phone, card, NINO and so on) are checked on the exact value only, because a fragment like `07700` identifies nobody. *Our call.* Every value has a non-empty exact text, so `NoRedactor` always scores 0.
- **Matching** is a plain substring search on the output. To stop a word from matching unrelated text, the 2.4 format check rejects a snippet where a `PERSON` or `ADDRESS` word also appears elsewhere in the same `text`.
- **Wrongly flagged:** a look-alike counts as wrongly flagged if it no longer appears exactly in the output.
- **Catch rate** = caught / planted, overall and per type.
- **Wrong-flag rate** = wrongly flagged / look-alikes, overall.

Step 2 ships two stand-ins for tests and `make eval`: `NoRedactor` (returns the text unchanged, catch rate 0) and `AnswerKeyRedactor` (removes exactly the planted values, catch rate 1, wrong-flag rate 0). `make eval` reports PII scores for `NoRedactor`, labelled as a stand-in. Step 4 swaps in Presidio.

The results file gains `redactor`, PII metrics, and per-snippet rows (caught, missed and wrongly flagged values).

**Tests:** the two stand-ins give 0 and 1. A partial name leak counts as a miss, a phone fragment left behind still counts as caught, a removed look-alike counts as wrongly flagged, and the per-type counts are right.

### 2.6 Answer grader

An AI model grades an answer with yes/no questions, which local models handle far more reliably than a 1–10 score:

1. **For each key fact:** "Does the answer state this fact?" The answer's score is the share of facts stated.
2. **Faithfulness**, once per answer: "Does the answer claim anything the retrieved code doesn't support?" This keeps the design doc's faithfulness metric. *Our call.*

Inputs: the question, its key facts, the answer, and the retrieved code text. Output: one yes/no per check, read with LangChain structured output. Temperature 0.

**Model and settings** are read by a small pydantic-settings class of their own in `evals/`, not by the app's `Settings`. The app's class requires `DATABASE_URL`, and evals run without a database. It reads the repo-root `.env`. *Our call.* Step 3 may move `CHAT_MODEL` into the app's settings when the bot needs it.

| Variable | Default | Meaning |
|---|---|---|
| `CHAT_MODEL` | `ollama:ornith:9b` | The bot's model, in `init_chat_model` form. Introduced here because the grader defaults to it. Step 3 uses it for the bot. |
| `EVAL_JUDGE_MODEL` | empty → copies `CHAT_MODEL` | The grader's model |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Where Ollama listens |

Changing provider is one env var, e.g. `EVAL_JUDGE_MODEL=anthropic:<model>`. Add these to `.env.example`. **Fix the grader model before step 7 compares bot models**, otherwise a changing grader muddies the comparison.

`ornith:9b` (5.6 GB) was picked to fit a 16 GB Apple M4 alongside Docker, from the Ollama library listing, not from experience. If the learning tests show it can't return structured yes/no replies reliably, try `ornith-1.5:9b` or `nimble-v3:9b`, and record the choice in the plan.

**Planted wrong answers:** `datasets/wrong_answers.yaml` covers ~10 questions from `questions.yaml`. Each entry holds:

- `question_id`
- `code`: a short hand-picked excerpt from the Oscar files (tens of lines, not whole files). It stands in for "retrieved code" until the bot exists, keeps the input within a 9B model's comfortable context, and lets 2.6 run without 2.3's fetch. *Our call.*
- `correct`: an answer that states every key fact and claims nothing outside `code`
- `wrong`: one or more answers, each written to fail in one way (a wrong rule, a made-up detail not in `code`, a vague non-answer, a correct answer to a different question), and each naming the check it should fail

**What counts as the grader getting it right** (*our call*):

| Answer | Grader is right when |
|---|---|
| `correct` | Every key fact is marked stated, and faithfulness is clean |
| `wrong` | The named check fails |

An entry with any `ungraded` check is **inconclusive**, and inconclusive counts as the grader getting it wrong. Success item 2 means every entry is handled right.

**When a reply can't be read**, the grader retries once and then records the check as `ungraded`. Ungraded checks are counted and shown in the summary, never treated as passes.

**Make:** `make eval-answers` grades every answer in `wrong_answers.yaml`, prints per entry whether the grader got it right, and saves a results file to `results/` in the same style as 2.3: `started_at`, `git_commit`, dataset version, the judge model and its settings, counts (right, wrong, inconclusive), and per-check rows. *Our call.* This is the record that shows the judge model stayed fixed before step 7. It stops with a clear message if Ollama isn't reachable.

**Dependencies:** `langchain`, `langchain-ollama`. Also `pyyaml` if 2.2 hasn't added it already.

**Tests:**
- **Unit tests** use LangChain's fake chat model, since the model provider is an unmanaged dependency. They cover fact scoring, the faithfulness flag, retry-then-ungraded, and the judge model copying `CHAT_MODEL` when unset.
- **Learning tests** pin `init_chat_model("ollama:…")` and structured output against a running Ollama. They are skipped, with the reason printed, when Ollama isn't reachable.

**Docs:** `tech-stack.md` gets the eval settings and Ollama as the local default. README gets setup lines: install the Ollama app from the `.dmg`, then `ollama pull ornith:9b`.
